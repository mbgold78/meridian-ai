## Context

Homepoc shipped the two halves of a diagnostic engine and deliberately never connected them. `ValidativeModeService` enforces the pinned P6 differential-grounding contract at candidate level (type/severity allowlists, required fields, CONTENT findings require ≥1 evidenceId resolving to an in-domain Evidence row, every survivor persisted as an `Assertion(AI_VALIDATIVE)`) — and **returns DTOs, never persisting `Finding`s** ("the caller decides whether to surface or commit"). `GenerativeModeService` mirrors this for `DraftEntity` ("Phase 2B's commit step does that"). Every `Finding` visible in the product today is fixture data (`DiagnosticSeeder`, `aiGenerated=false`, `createdBy='seed'` — seam S2). Ingestion (C6) is built and Tester-proven: it writes a REAL evidence chain (`Evidence` per committed entity → `DocumentRegistry` → `ingest_runs`), has exit codes 0/1/2/3 with `INGEST_EVENT` lines, and the Glacier corpus (6 systems, 6 deliberately defective manual processes, entities, workflow notes) sits at `substrate/ingestion/samples/`. `SynthesisRun` already carries runType/status/token/cost columns; `Finding.synthesisRunId` is already a soft FK.

Two designs were produced (evidence-chain-first vs pipeline-first) and judged. **The evidence-chain-first design won** on P6/P7 fidelity (findings.assertion_id as a first-class column; a provenance-walk read model shipped FIRST; durable per-item human curation events; no bulk-accept verb) and on implementability — it found the single most consequential fact in either design, verified on disk: **`GetEvidenceForFindingTool` is the only evidence-touching tool and requires an existing `findingId`, so against freshly-ingested data the LLM cannot learn valid Evidence UUIDs, and the differential-grounding filter structurally zeroes out ALL CONTENT findings.** Without the fix (D6 below), the real CONTENT lane is dead while mock-scripted CI stays green — the exact silent false-PASS the audit-defensibility contract exists to prevent. Eight specific grafts from the pipeline-first design are folded in below (marked *graft*): the batch ledger/resume model, the dev-shared profile that makes local E2E actually run cross-process, the zero-yield trichotomy, the differential findingType defaults, the enriched evidence snapshot, the precise stall definition, the thin V8 initiatives slice, and the one-active-run lock + lane-fallback semantics.

Binding constraints: **[EVIDENCE-GROUNDING]** (AI output → Assertion → Evidence → DocumentRegistry → Reader source; all generative output lands DRAFT requiring per-item human acceptance; ungrounded AI output is filtered, never presented; deterministic lenses compute, the LLM narrates but never generates analytics — P7); **one-directional orchestrator seam** (agents are advisors, never mutators); **whole-or-in-part** (degraded mode without orchestrator); **read-model-first sequencing**; **flag-not-invent**; **decline/pause/reject never error-colored**; **acceptance must be user-runnable**; **no-silent-zero-yield**; Testcontainers-Postgres is the CI gate (no Docker on this dev machine).

**Binding-input provenance correction (recorded for the file):** `meridian-homepoc/frontend/src/demo/beacon/agents.ts` does not exist. Agent fixture truth is `BeaconAgent` in `types.ts` + per-subsidiary fixture files, rendered by `OperationsTab.tsx`. D3's registry design and D5's agent-stat composition must work from those.

## Decision

### D1 — The commit step is a downstream pipeline stage; the pinned mode services stay byte-identical

`com.meridian.substrate.engine.diagnostic` consumes `FindingCandidate`/`DraftEntity` DTOs; the mode services' allowlist + differential-grounding contracts port-map §2.3 pins ("keep VERBATIM — best-tested logic; phase2a tests pin them") are not modified. The parse→allowlist→grounding-filter→Assertion core of `ValidativeModeService` is extracted into a reusable `CandidateFilter` collaborator with **no behavior change** (the mode service's public contract and pinned phase2a tests stay green), so that orchestrator-dispatched agent output re-enters through the *exact same* filter as in-process output. Substrate is the only enforcement point; the agent is never trusted.

**Alternatives considered:** committing inside the mode services (rejected — mutates the pinned surface and couples generation to persistence); a separate validation path for dispatched results (rejected — two filters drift; the whole point is one chokepoint).

**REVISIT TRIGGER:** any pinned phase2a test needing a *semantic* edit is a scope alarm and grounds to stop (*graft* — the pipeline design's discipline, applied to A's architecture).

### D2 — `SynthesisRun` IS the run record; a new `diagnostic_run_batches` ledger is the atomicity/resume unit (*graft*)

No new run table: a diagnostic run is a `SynthesisRun` row (`runType='diagnostic'`), status vocabulary `{PLANNED, RUNNING, COMPLETED, COMPLETED_WITH_ERRORS, ZERO_YIELD, FAILED, CANCELLED}` documented, not enum-tightened (free-text status fields port AS-IS). Token totals from `OrchestratorResult` and a cost estimate are persisted per run **with the `substrate.llm.cost.*` rates snapshotted into metadata** (rates drift; audits don't) — this severs S12 durably for the diagnostic path; `CostTracker` stays the in-memory process aggregate.

The run is planned into batches recorded in `V7`'s `diagnostic_run_batches` (*graft*, replacing the winner's all-or-nothing per-run commit): **the batch is the atomicity unit** — LLM generation happens OUTSIDE any transaction; finding commits + batch-ledger update + run counters happen in ONE transaction. A crash between generation and commit leaves the batch RUNNING with a stale `claimed_at`; resume treats stale RUNNING as FAILED and re-executes — duplicates are impossible because a failed batch committed nothing. `resume`/`cancel` endpoints; per-batch `candidates_returned`/`candidates_filtered`/`findings_committed` + filter-reason histogram. One bad batch no longer voids an expensive run (the winner's admitted weakness); the fragile `@Async`-plus-startup-sweep orphan story is replaced by the ledger.

**Alternatives considered:** all-or-nothing per-run commit (the winner's original shape; rejected per graft — one bad row voids the whole spend); a dedicated job-infra table (rejected — `synthesis_runs` + ledger is sufficient at human-paced volume); cross-LLM-run semantic dedupe (rejected — the tx boundary is the dedupe; semantic dedupe is invented complexity).

**REVISIT TRIGGER:** real job infrastructure landing for any other engine; batch-ledger growth/retention at engagement scale.

### D3 — Supersession is a run-finalization-transaction step, never a per-batch step

Because batches commit incrementally (D2), the winner's supersession semantics are redefined (resolving the judge's named open tension): when a run finalizes as `COMPLETED` or `COMPLETED_WITH_ERRORS`, the finalization transaction marks prior findings of the same `(domainId, scope-set)` that are still `PENDING_REVIEW` **and were not created by this run** as `SUPERSEDED` (curation event recorded, `synthesis_run_id` = superseding run). `ACCEPTED`/`REJECTED` findings are never touched. `ZERO_YIELD`/`FAILED`/`CANCELLED` runs supersede nothing — a deficient run must not wipe the prior pending set. A mid-run crash therefore leaves prior PENDING rows honestly co-present with the new run's committed rows until resume finalizes; the transient window is visible (every row carries `synthesisRunId`), accepted, and tested. Idempotency is honestly scoped to bookkeeping — LLM content varies run-to-run; the mock provider pins CI determinism; `SynthesisRun` lineage is how auditors compare runs.

**Alternatives considered:** supersede-per-batch (rejected — partial supersession by an incomplete run is the worst audit shape); supersede-before-commit (the winner's original; rejected — incompatible with incremental batch commits).

**REVISIT TRIGGER:** operator triage fatigue from overlapping-scope runs accumulating near-duplicate pending findings (scope normalization is a flagged Mike question, not built).

### D4 — Evidence chain is first-class data: `findings.assertion_id` column + unified append-only `ai_curation_events` (V7 + V7_1)

The Finding→Assertion hop is the audit walk's first link, not a metadata footnote: `V7` adds `findings.assertion_id` (soft ref, app-enforced per the canonical-model convention) plus curation projection columns (`curation_status`, `curated_at`, `curated_by_label` — the cascade D11 denormalized-label idiom). Curation truth lives in a unified append-only `ai_curation_events` table covering BOTH committed-finding curation and generative-draft curation: `subject_kind ∈ {FINDING, DRAFT}`, `action ∈ {ACCEPT, REJECT, SUPERSEDE}`, rationale (service-enforced NOT NULL for REJECT), `overridden_fields` JSON delta for human-edited draft accepts, mandatory idempotency key with a DB UNIQUE backstop. `V7_1` (postgresql) adds the append-only trigger (V4_1 precedent) — H2 dev is service-enforced only; CI is the gate. Rejection is data: the row stays, default list queries exclude it, `?includeRejected=true` restores it; ACCEPT-after-REJECT is legal recourse (append another event; last event wins the projection) — operator mis-click recovery without ever deleting history.

**Alternatives considered:** curation status as a mutable column only (rejected — discipline is not a structure; the accountability act deserves its own attributed, timestamped record); separate finding-curation and draft-curation tables (rejected — same lifecycle, same audit consumer); a new draft table for generative output (rejected — the `AI_GENERATIVE` Assertion row already holds `proposedFields` and IS the durable draft store; rejection then needs no entity row at all).

**REVISIT TRIGGER:** Phase 5 OIDC (actor labels become IAM-stable; re-verify curation-actor guards — until then curation identity is spoofable persona headers, S9 posture, must be stated in any compliance conversation).

### D5 — Audit defensibility is a read model shipped FIRST: provenance walk + verify sweep

`GET /api/v1/findings/{id}/provenance` materializes the full P6 chain in one response: finding → assertion (subject/predicate/object/confidence/producedBy) → evidence[] (label, confidence, sourceFile, extractor) → documentRegistry[] (sha256, ingestionStatus, processedByConverterRunId) → ingestRuns[] → readerRegistration (when traceable), plus `chainComplete: boolean` and `groundingMode`. A dangling hop sets `chainComplete=false` — surfaced, never silently elided. `GET /api/v1/diagnostics/verify?domainId` walks every aiGenerated finding and reports broken chains and fixture-grounded chains (`extractor='seed'`) as distinct classes — the diagnostic twin of `/decision-log/verify`. Both land in build-order step 2, **before any generation exists**, working against DemoPack data (read-model-first; user-runnable curl acceptance from day one).

**REVISIT TRIGGER:** none — this is the binding sequencing rule applied; only the DTO shape may flex with the C9 dashboard swap.

### D6 — Close the citation-vocabulary gap: a `find_evidence` read tool over `RelationalEvidenceRetriever`

Verified on disk: the tool inventory exposes `get_evidence_for_finding` only, which **requires an existing findingId** — against freshly-ingested data the model has no way to discover domain evidence UUIDs, so every CONTENT candidate would fail the grounding filter (ValidativeModeService line 165) and the real CONTENT lane silently zeroes out. D4 adds a read tool `find_evidence(domainId, entityId?, entityType?)` backed by the existing (well-shaped, previously unwired — dead-code-mirage list) `RelationalEvidenceRetriever`, registered as a Tool bean with persona-access defaults and named in the VALIDATIVE and GENERATIVE prompts. Run metadata records grounded-rate; a run where ALL CONTENT candidates were filtered emits a loud `DIAG_EVENT kind=all_content_filtered` (no-silent-zero-yield applied to grounding). Because this extends the pinned phase2a prompt/tool surface, `MockAnthropicClient` scripted tool-call cases must prove the addition does not perturb existing eval expectations (*graft* discipline, judge's named tension).

**Alternatives considered:** dumping evidence inventories into the prompt (rejected — context bloat, no pagination, defeats the tool-calling architecture); leaving CONTENT findings to operator authoring (rejected — that IS the dead lane; B's design never addressed this and its own real-lane acceptance was unsatisfiable as designed).

**REVISIT TRIGGER:** vector/document retriever replacing `RelationalEvidenceRetriever` (the port-map already names it as the natural seam).

### D7 — S3 honesty: existence-only grounding is first-class data; human curation with inline evidence is the compensating control

`groundingMode='EXISTENCE_ONLY'` is persisted in finding metadata and surfaced in every provenance DTO and the curation UI. Product copy contract: "evidence citations are existence-verified; semantic support is human-verified at acceptance" — never "machine-verified grounding". The curation surface is the named compensating control: the accept affordance MUST render the cited evidence inline (labels, source files, registry links via the provenance walk) so the human is verifying semantic support, and the ACCEPT event is the durable record that a named human did so. A `GroundingVerifier` SPI ships with the single `ExistenceGroundingVerifier`; a future SEMANTIC verifier (LLM-judge or embedding score) is an extension point that is **advisory-only by contract** — it may lower confidence, never auto-pass (P7: an LLM opinion about grounding is itself an AI claim). Granularity limit stated plainly: Evidence rows are document-level ("Committed from systems.csv"), so human semantic verification is coarse; passage-level evidence via the existing `EvidenceChunk` seam is named future work, and the audit-defensibility claim must state this limit until then.

**REVISIT TRIGGER:** EvidenceChunk/passage-level retrieval landing; regulated-buyer demand for machine-assisted semantic scoring.

### D8 — Commit-step mapping: explicit, pinned, and never silently lossy

`FindingCandidate → Finding(aiGenerated=true, status=OPEN, synthesisRunId, assertionId, curationStatus=PENDING_REVIEW)`. Severity: CRITICAL→CRITICAL, HIGH→HIGH, MEDIUM→MEDIUM, **INFO→LOW** (documented lossy mapping). FindingType (*graft*): the candidate JSON contract gains an optional `findingType` field validated against the canonical 12-value enum; when absent or invalid, **differential defaults** apply — STRUCTURAL→`COVERAGE_GAP`, CONTENT→`DATA_QUALITY` — with `metadata.findingTypeDefaulted=true`, and an invalid LLM-supplied type never discards an otherwise-grounded candidate. `title` is an optional candidate field with first-sentence-of-description fallback (truncated 200; `findings.title` is NOT NULL). The persisted `evidence` JSON is the **enriched snapshot** (*graft*) `[{evidenceId, label, sourceFile, documentRegistryId, confidence}]` joined from the grounding-validated Evidence rows — findings are self-describing for rendering, and snapshot-vs-live drift is detectable via the D5 `chainComplete` walk. `affectedSystemIds`/`affectedProcessIds` populate from `affectedEntityType+affectedEntityId` after an in-domain existence check (unresolvable → `metadata.unresolvedAffectedEntity`, finding still commits). No duplicate Evidence rows are ever minted. STRUCTURAL findings legitimately end their chain at the Assertion (self-justifying model-state observations per the pinned contract) and render evidence-less distinctly, never error-colored.

**Alternatives considered:** single DATA_QUALITY bin for all defaults (the winner's original; rejected per graft — STRUCTURAL findings are coverage observations, not data-quality claims); discarding candidates with invalid findingType (rejected — a grounded claim should not die on a vocabulary miss); minting fresh Evidence rows per finding (rejected — duplicates the chain and corrupts provenance counts).

**REVISIT TRIGGER:** first real-corpus run review with Mike — INFO→LOW and the findingType defaults shape dashboard severity distributions before he has reviewed them (named, unresolved by both designs); consider deterministic structural validators replacing LLM STRUCTURAL findings entirely (more P7-aligned).

### D9 — Generative commit: the Assertion is the draft store; human acceptance is per-item and structural

`DraftCommitService.commitDraft(assertionId, overrides?, persona)`: require `producedBy=AI_GENERATIVE ∧ predicate='proposes_creation' ∧ not-already-curated`; **re-verify every evidenceId still resolves in-domain at commit time** (grounding is re-checked at materialization, not just proposal); materialize `Capability(status=DRAFT, aiGenerated=true)` with the `parentId→parentCapabilityId` rename the GenerativeModeService javadoc contract assigns to this step. Human `overrides` apply AFTER the asserted fields and the delta is recorded on the ACCEPT curation event — the human edit is itself provenance. Per-item acceptance is structural: **no bulk auto-accept verb exists** (P6/doc-07); a batch-accept affordance is a flagged Mike product question, and even if granted would emit one event row per item. Capability is the only materialization target in v1 (the only entity type with a mode-service allowlist); others are a named extension point.

**REVISIT TRIGGER:** second entity type shipping through the generative path; Mike's batch-accept ruling.

### D10 — Curation gate + list-filter defaults: PENDING_REVIEW findings are operator inventory, not client content — flagged as an assumed product decision

Committed AI findings land `PENDING_REVIEW` and do not reach client (COO) surfaces until a named human ACCEPTs; existing list endpoints (`GET /ecosystem/findings`) gain the default filter `curation_status NOT IN (REJECTED, SUPERSEDED) OR curation_status IS NULL` plus additive `?curationStatus=`/`?includeRejected=`/`?aiGenerated=` params; client-surface composition additionally excludes `PENDING_REVIEW`. NULL means "not subject to curation" (operator/fixture rows; `DiagnosticSeeder` rows stay NULL — demo behavior unchanged). **This is a product behavior homepoc never had** and it determines `surfacedAt` semantics (D13). Both designs only assumed an answer; this ADR encodes the gate because it is the load-bearing S3 compensating control (D7), and flags the visibility question to Mike explicitly. The default-filter change silently alters existing consumers — a frontend grep-audit is a named implementation step (endpoints-barrel-omission trap precedent).

**Alternatives considered:** AI findings visible immediately with a "pending" badge (B's implicit posture; surfacedAt=createdAt) — simpler, but guts the compensating control; rejected pending Mike's ruling, documented as the one-line projection change if he overrules.

**REVISIT TRIGGER:** Mike's curation/visibility product session — top follow-up item.

### D11 — Two executors, one filter: in-process is the base case; the orchestrator lane is optional, governed, and falls back

`DiagnosticExecutor` SPI. `InProcessDiagnosticExecutor` (default, always present) calls `ValidativeModeService` directly against `substrate.llm.*` — **degraded mode loses nothing but the dispatch lane** (degradation is a missing bean, no parallel code path). This deliberately upgrades the contract doc's degraded-mode line ("Diagnostics (Phase 4): operator-authored findings instead of AI generation", `orchestrator-substrate-contract.md` line 53) — consistent with whole-or-in-part, and the contract doc gets a versioned amendment at slice close so the deviation is not silent (judge's named tension; follow-up #5). `OrchestratorDiagnosticExecutor` (`@ConditionalOnProperty(substrate.orchestrator.enabled)` AND `substrate.diagnostic.executor=orchestrator`) is the engine's ONLY orchestrator touchpoint, mirroring cascade D14: `check_budget_for_task` → `submit_task(task_type=diagnostic-generation, context packs as read-API URLs)` → non-blocking poll → `get_dispatch_result` candidate JSON → **re-enters through the same `CandidateFilter`**, applied as a `GovernedAction(actionType=apply_dispatch_result, principal=SERVICE)` — ADR-002 PEP #3. `get_dispatch_events` digest lands in run metadata. *Graft:* budget refusal or dispatch failure → `substrate.diagnostic.dispatch.fallback = in-process (default) | skip`; fallback is recorded in batch metadata; `SKIPPED_BUDGET` renders neutral (budget refusal is a governance non-event per the contract doc). *Graft:* one active run per domain, enforced 409 `DIAGNOSTIC_RUN_ACTIVE` under a domain-scoped service lock (PG partial-unique backstop in the vendor migration). Known dependency: `OrchestratorMcpClient` has no production transport until Phase-3 MCP SDK work — the orchestrated lane can slip without blocking anything (build-order step 8).

**REVISIT TRIGGER:** agent-proposed findings as AGENT principals over governed MCP tools (rides the D3 registry; never a bypass); MCP transport landing.

### D12 — Governance: every new write verb is `@Governed`; the diagnostic CLI gets NO exemption; curation is not hash-chain-mirrored

`diagnostic.commit_findings` (SERVICE, in-process lane), `apply_dispatch_result` (SERVICE, orchestrated lane), `finding.accept`/`finding.reject`/`capability.commit_draft`/`capability.reject_draft`/`initiative.update_progress` (HUMAN persona principals). Annotations land now (inert until contracts 3c ships the gateway; shadow-mode default makes the retrofit safe; ArchUnit governed-coverage picks the package up automatically). Unlike D3-ingestion's `@UngovernedModule` (ADR-002 D3: operator-curated pre-activation data), the diagnostic runner executes through the same governed services with **no exemption** — diagnostics run on possibly-ACTIVE engagements. Per-item finding curation is NOT mirrored into the `engine.decision` hash chain (volume/append-lock contention — ADR-002 D14's bounded-mirroring rationale); a `DiagnosticAttestationHook` seam (no-op default, ADR-001 D15 idiom) can anchor a per-run digest (run id + ordered accepted-finding hashes) behind `substrate.diagnostic.attest-to-decision-log` (default false).

**REVISIT TRIGGER:** regulated-buyer demand for curation tamper-evidence (implement the hook); contracts 3c landing (verify shadow-mode decisions appear for these actionTypes).

### D13 — D5 statistics are deterministic read-time compute; contract stats are delegated, never duplicated; surfacedAt = ACCEPT-event time

`PortfolioReadService` + `GET /api/v1/portfolio` and `GET /api/v1/portfolio/subsidiaries/{domainId}` speak fixture vocabulary at the `BEACON_PORTFOLIO` swap seam (cascade D13 idiom). All numbers are read-time SQL/Java compute over existing tables — no stats tables, no LLM anywhere in the path (P7). Exact formulas live in the spec §12; the decisions of record:

- **lifecycleStallCount** (*graft* precision): current phase = highest-order sequenced phase (DESIGN..AUTOMATE; PLUG_IN excluded as continuous) with status IN_PROGRESS or BLOCKED; stalled := BLOCKED, OR IN_PROGRESS with `now − max(enteredAt, updatedAt) > substrate.stats.stall-threshold-days` (default 90 — config knob, not invariant); checkpoint/blocker edits count as movement via updatedAt. Domains with no PhaseState rows are a separate `unphased` count — never silently folded in (no-silent-zero-yield applied to stats).
- **coordinationPatternsThisWeek** + **pendingFederationInvitations** — DELEGATED to the contract engine's `ContractSignalService` (contracts spec §11.2 owns these computations); `PortfolioReadService` composes the same bean — one computation, two surfaces, no drift. *Graft:* every stats DTO carries per-source sub-counts + a `computedFrom` meta block, so pre-D2-3b the contract terms contribute 0 **visibly**. B's richer union (monitor signals, sibling-decline advisories) exceeds §11.2's definition — v1 ships the §11.2 number; growing it is a named SignalService-spec amendment, not a portfolio-side fork (judge's named tension, resolved in favor of ownership).
- **surfacedAt** — for aiGenerated findings, the `curated_at` of the ACCEPT event (the moment a finding became client-visible, per the D10 gate); for operator/fixture findings, `createdAt`. If Mike overrules D10, this becomes `createdAt` everywhere — a projection change only.
- **progressPct** (*graft*, replacing the winner's `initiatives: []` refusal): a thin tracked V8 slice of doc-06's schema — `transformation_plans` + `transformation_initiatives` with operator-maintained `progress_pct`/`progress_note`/`progress_updated_at`; the ONLY computed rule is status=COMPLETE ⇒ 100. Port-map S6 itself says "progress from initiative tracking", so an operator-tracked slice is the honest sever; the planning engine (waves, rationalization lens, plan state machine) remains S4 future work and the fixture `/transformation/plan` endpoint stays behind its flag. **Declared S4 deviation**, cheap under the fresh-DB posture, flagged at slice close.
- **Agent stats** — composed from the D3 registry (V6) when the bean is present; absent → `agentsAvailable:false`. **aiReadiness is omitted, not invented** (no computation basis until D3's readiness lens).
- Finding rollups exclude REJECTED/SUPERSEDED (and PENDING_REVIEW on client surfaces) by default — curation directly shapes the executive numbers, which is the point: a rejected AI claim never silently inflates a dashboard.

**Alternatives considered:** deriving progress from cascade/phase activity (rejected — fabricated analytics, the named demo-pressure failure mode); duplicating the §11.2 computation portfolio-side with a richer union (B's shape; rejected — drift risk against the owning engine); materialized stats tables (rejected v1 — counts are cheap indexed queries; REVISIT at >50 domains or aggressive polling).

**REVISIT TRIGGER:** first-engagement calibration of stall threshold/pattern window; S4 planning-engine design (may reshape V8 — flag at slice close); D3 readiness lens landing (aiReadiness becomes computable).

### D14 — Acceptance is user-runnable end-to-end on this machine: the `dev-shared` profile (*graft*), with Testcontainers-Postgres as the only gate

Verified gap: app dev profile is `jdbc:h2:mem:substrate` while ingestion dev is `jdbc:h2:file:./data/ingestion-dev` — the winner's 7-step local acceptance as written would hit two different databases. Fix (*graft*): a new app profile `dev-shared` on `jdbc:h2:file:./data/engagement-dev;AUTO_SERVER=TRUE;MODE=PostgreSQL;…` and ingestion's dev profile realigned onto the same file DB (the `./data/ingestion-dev` path is retired — one-line breaking dev change, flagged), so the documented ingest-CLI → diagnostic-run → curl E2E actually runs cross-process on the Docker-less machine. The CI gate remains a **single-JVM Testcontainers-Postgres e2e** (ingestion services + diagnostic run + scripted `MockAnthropicClient` emitting one grounded CONTENT candidate citing real Evidence ids read from the DB, one ungrounded candidate that must filter, one invalid-severity candidate) — H2-green is never acceptance. Zero-yield trichotomy (*graft*) folded into the CLI exit-code matrix: zero parseable candidates anywhere = ALWAYS hard fail (`NO_CANDIDATES`, distinct from all-filtered); all-filtered = `ZERO_YIELD` only when `requiredMinFindings>0`, else `COMPLETED` with mandatory explanation + per-batch filtered counts; committed < requiredMinFindings = `ZERO_YIELD`. Real-LLM acceptance discipline (*graft*): exactly ONE framed re-run permitted under the tactical-retry rule, with the run-detail artifact preserved at a durable Mike-accessible path before any worktree reap. Because a real Glacier run can legitimately yield STRUCTURAL-only findings (evidence-optional by the pinned contract), **whether STRUCTURAL-only satisfies the port-map D4 acceptance wording ("Assertion+Evidence chains") needs an explicit ruling** — encoded here as: STRUCTURAL-only passes the run gate but emits `DIAG_EVENT kind=no_content_findings`, and the question is surfaced to Mike (follow-up #6) so the first operator run does not relitigate it.

**REVISIT TRIGGER:** H2 AUTO_SERVER misbehavior under cross-process access (it is acceptance convenience, never the gate); Mike's STRUCTURAL-only ruling.

### D15 — Delivery is strictly read-model-first

(1) V7/V7_1 + entity/repo changes → (2) provenance walk + verify endpoints against DemoPack (user-runnable before any generation) → (3) `find_evidence` tool + `CandidateFilter` extraction (no behavior change) → (4) run lifecycle + batch executor + commit step + in-process executor + REST + CLI (mock acceptance) → (5) curation + list filters + supersession → (6) generative commit → (7) Glacier E2E + Testcontainers suite + eval expansion → (8) orchestrator executor (can slip) → (9) D5: V8 + `PortfolioReadService` + endpoints + dashboard swap at `BEACON_PORTFOLIO`. `gradlew build` green at every boundary; acceptance at every step is boot + curl/CLI.

**REVISIT TRIGGER:** none — binding sequencing restated for the record.

## Consequences
